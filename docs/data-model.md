# Data model & storage design

Detailed rationale behind the storage architecture and reference-data pipeline.
CLAUDE.md carries the condensed invariants; this file is the full reference.
The *actual* schema is defined in code — reference tables' raw SQL DDL in
`src/db/schema.ts`, personal tables' shape in `src/db/schema/personal.ts`
(Drizzle), with `src/db/types.ts` as the separate, hand-written TS interface
source the rest of the app codes against (see "Migration runner (Drizzle)"
below and docs/architecture.md's DB layer table for how these relate) — the
DDL block below is the reasoned proposal they grew from, kept for the design
rationale in its comments.

## Storage

- **SQLite on-device** via `@tauri-apps/plugin-sql`. No IndexedDB, no
  browser storage — this is a native-wrapped app, so there's no reason to
  target browser-only APIs.
- Two logical groups of tables, separated so that app updates can never
  destroy user data:
  - **Reference tables** — the Pokédex itself (species, forms, mega variants,
    types, regions, backgrounds). Wholesale replaceable on every update. The
    app owns this data, not the user.
  - **Personal tables** — the user's own achievement state. Never written by
    an update, only by user interaction.
- Every reference row has a **permanent, immutable slug** as its primary key
  (e.g. `bulbasaur-standard-male`, `charizard-mega-x`), generated once and
  never reused or reassigned across versions. Personal-data rows reference
  reference rows by this slug (foreign key). This is what makes reference-table
  replacement safe — as long as slugs are stable, updating the dex never
  orphans a user's data.
- All achievement/personal facts are **real boolean columns**, not list values or JSON blobs. Combined milestones (e.g. a shiny + perfect-IV
  individual, i.e. "shundo") are **independently stored facts, never
  computed from other booleans** — two independently-true flags (e.g. owns
  *a* shiny, owns *a* hundo) do not imply the same individual was both, so
  the combined fact must be its own column, entered/verified independently.
- Include a small schema-version table and a migration runner for personal
  data, so future additions to the personal schema can run a one-time
  migration on load without touching reference data.

## Versioning policy — two separate mechanisms, don't conflate them

There are two independent version numbers in this codebase. Bumping the
wrong one (or neither) when the underlying thing changes is the failure
mode to avoid:

- **`CURRENT_PERSONAL_SCHEMA_VERSION`** (`src/db/schema.ts`) — covers the
  *structure* of the personal tables (`species_personal`, `form_personal`,
  etc.), not their contents. Bump this by hand **whenever a personal-table
  column is added, removed, renamed, or its meaning changes** (e.g. adding a
  new achievement boolean like `four_star_dynamax`) — edit
  `src/db/schema/personal.ts` and run `npm run db:generate` to produce the
  matching migration (see "Migration runner (Drizzle)" below); there is no
  `MIGRATIONS` array to append to anymore. This constant is also the version
  number stamped into Settings → Export files and checked on Import (see
  `src/data/repository.ts`'s `PersonalDataExport`), so an out-of-date bump
  here would let a structurally-mismatched export get imported without
  warning.
- **`reference_data_version`** (`src/db/reference-sync.ts`) — covers the
  *contents* of `src/data/reference.json` (new species, new forms, new
  costumes, corrected flags, etc.). This one is **automatic** — it's a
  content hash of the whole file, recomputed and compared on every app
  start, and triggers a reference-table wipe-and-reload whenever the file
  changes. **Nothing to bump by hand here**: adding new Pokémon or editing
  existing reference data (via the ingestion pipeline or CSV tools) is
  enough on its own; the version updates itself.

### Migration runner (Drizzle)

Personal-table migrations are generated by drizzle-kit (`npm run db:generate`, reading `src/db/schema/personal.ts`) and applied by a hand-rolled runner in `src/db/migrations.ts`, tracked in Drizzle's own `__drizzle_migrations` table — this replaced a hand-rolled versioned runner (`schema_version` + a manually-written `MIGRATIONS` array) that shipped through v1.0.0. It is **not** `drizzle-orm/sqlite-proxy/migrator`'s own `migrate()`: that function's `readMigrationFiles()` reads migration files off disk via Node's `fs` module, which doesn't exist on either platform this app ships to (Android or desktop, both via `@tauri-apps/plugin-sql` — neither has filesystem access to read migration files directly) — each migration's SQL is instead embedded as a string constant (`src/db/migrations-data.ts`, generated by `npm run db:generate-data`) and applied with equivalent compare-and-apply logic that needs no filesystem access.

There are five migrations. Migration `0000` encodes the schema real shipped devices actually have on disk (`TEXT` timestamp columns, matching the old hand-written schema verbatim — real devices are known to be at hand-rolled personal-schema v5 or v6; the v1.0.0 tag's schema v2 was never actually distributed) — not personal.ts's final shape. Migration `0001` then converts every timestamp column from `TEXT` to `INTEGER` (Drizzle's `integer({ mode: 'timestamp_ms' })`) via a genuine SQLite table-rebuild (create a new table with the target shape, copy rows across converting each timestamp value with a `julianday()`-based SQL expression, drop the old table, rename), applied on every device — fresh installs (a no-op over empty tables) and upgrading v5/v6 devices (the real conversion) alike. This split exists because SQLite column affinity is fixed at `CREATE TABLE` time: an in-place `UPDATE` into a `TEXT`-affinity column can't actually change its storage class, so a single migration that declared these columns `INTEGER` from the start would have looked like it worked while silently corrupting every existing timestamp the first time it was read back through Drizzle's `timestamp_ms` mode.

Devices that installed before this change are bootstrapped once: `src/db/migrations.ts` detects the old `schema_version` table, defensively creates `player_progress_log` if it's missing (the one table a genuine v5 device lacks relative to v6), and seeds `__drizzle_migrations` with a row for migration `0000` only (not `0001`) — this tells the runner "this device is already at the schema it truly has on disk," so `0000`'s `CREATE TABLE` statements are never replayed against tables that already exist, while `0001` is picked up as genuinely pending and runs normally. `PRAGMA foreign_keys` is toggled off around the whole pending-migrations transaction (not inside migration `0001`'s own embedded PRAGMA statements, which are inert once wrapped in a transaction — SQLite refuses to change `foreign_keys` enforcement mid-transaction) since `0001`'s rebuilt tables carry `REFERENCES` clauses into reference tables that don't exist yet at this point in boot (`syncReferenceData()` creates them afterward). See `src/db/migrations.ts`'s module comment for the exact mechanism.

Reference tables are **not** part of this migration system — `src/db/schema/reference.ts` exists only for typed queries, and drizzle-kit's config (`drizzle.config.ts`) only ever points at `schema/personal.ts`. Reference tables keep the existing wholesale drop/recreate model (`reference-sync.ts`).

The `TEXT` → `INTEGER` timestamp change isn't only a DB-column detail: every personal-table timestamp field in `src/db/types.ts` (`updatedAt`/`recordedAt`/`caughtAt`/`createdAt`) is typed `number` (epoch milliseconds via `Date.now()`), not `string`, and every read/write site (`in-memory-store.ts`, `sqlite-repository.ts`, `defaults.ts`'s `NEVER_UPDATED` sentinel) was updated to match — this is why `CURRENT_PERSONAL_SCHEMA_VERSION` bumped 6 → 7. `personal-data-transfer.ts`'s `readPersonalDataFile` detects a pre-7 export file (still ISO-8601 strings) and converts every timestamp field to epoch-ms before the data ever reaches `importPersonalData`'s numeric merge comparisons — without that, a number-vs-string comparison silently picks the wrong side of a merge and reinjects a string into an `INTEGER` column.

Migration `0002` makes `pokemon_instance.iv_percent` a genuine SQL
`GENERATED ALWAYS AS (...) VIRTUAL` column, derived from three new
`iv_attack`/`iv_defense`/`iv_stamina` columns (each `INTEGER`, `CHECK`
0–15) instead of a hand-typed value — this is why
`CURRENT_PERSONAL_SCHEMA_VERSION` bumped 7 → 8. Like `0001`, this is a
genuine table-rebuild (SQLite can't `ALTER TABLE` a column into being
generated), applied identically on fresh installs and upgrading devices;
the same `PRAGMA foreign_keys` toggle-around-the-whole-transaction
mechanism described above covers it too, since the rebuilt
`pokemon_instance` table carries `REFERENCES` clauses into `form`/
`profile`/`backgrounds`. A pre-`0002` device's existing `iv_percent`
values (hand-typed, no component breakdown to derive from) are not
carried forward — an intentional, owner-confirmed decision (see
`docs/superpowers/specs/2026-07-24-sub-project-4-iv-entry-rework-design.md`),
not an oversight.

Migration `0003` adds two new `pokemon_instance` columns, `dynamax` and
`received_via_trade` (both `INTEGER` boolean, `NOT NULL DEFAULT false`,
each with its own named `CHECK (col IN (0, 1))` constraint following the
existing `shiny`/`lucky`/`shadow`/`purified` pattern) — this is why
`CURRENT_PERSONAL_SCHEMA_VERSION` bumped 8 → 9. Despite being a plain
column addition, drizzle-kit still generated a full table-rebuild (adding
a `CHECK` constraint to an existing table isn't expressible as an
in-place `ALTER TABLE ADD COLUMN` in SQLite), so it needed the same
hand-fix as `0002`: dropping `iv_percent` from the rebuild's
`INSERT ... SELECT` (a `GENERATED` column can't be an INSERT target) and
dropping the two new columns from the `SELECT` side, since the *old*
`pokemon_instance` table being copied from doesn't have them yet — every
pre-existing row picks up the column default (`false`) instead.

Migration `0004` is Sub-project 7a's local multi-account migration — this is
why `CURRENT_PERSONAL_SCHEMA_VERSION` bumped 9 → 10. It retypes `profile.id`
from `INTEGER AUTOINCREMENT` to `TEXT` (a UUIDv4, generated at profile
creation, including for the migrated pre-existing single profile) and adds
`profile.is_current` (boolean; the invariant is exactly one profile row has
this `true` at any time). Five personal tables — `species_personal`,
`form_personal`, `mega_personal`, `form_background_personal`, and the
newly-per-profile `app_settings` — get their primary key widened to include
`profile_id` via the same table-rebuild pattern as `0001`-`0003` (SQLite can't
`ALTER TABLE` a PK). Every other personal table that already carried
`profile_id` as a plain column (`pokemon_instance`, `tag`,
`player_progress_personal`, `player_progress_log`,
`medal_progress_personal`) is rebuilt too, purely to retype that column from
`INTEGER` to `TEXT` — no PK shape change. `pokemon_instance.id`/`tag.id`
themselves stay local `AUTOINCREMENT` integers; giving those a stable
cross-device identity is out of scope here (deferred to Sub-project 7b, see
[roadmap.md](roadmap.md)). Every pre-existing row's `profile_id` is rewritten
unconditionally to the new UUID as part of the migration — this closes out
the "possible latent `profile_id` mismatch on existing rows" concern carried
forward from Sub-project 2 (see roadmap.md), since there is no longer a
by-value match to get wrong. Because `app_settings` is now per-profile and its
`profile_id` column is `NOT NULL` with a `REFERENCES profile(id)` FK, it can
no longer hold a genuinely global value — `reference_data_version` is moved
out to a new, non-profile-scoped `app_meta` table (`key`/`value`, no
`profile_id` at all) as part of the same migration. Like `0001`-`0003`, this
needed hand-fixes to drizzle-kit's generated rebuild: restoring every
`REFERENCES` clause the rebuild drops (including the five new/retyped
`profile_id -> profile(id)` FKs), dropping `pokemon_instance.iv_percent` from
the `INSERT`/`SELECT` lists (still a `GENERATED` column), and seeding
`app_settings.profile_id` and `app_meta` from the pre-migration
`(key, value)`-only `app_settings` table before dropping it. See
`src/db/migrations/0004_empty_vapor.sql`'s header comment for the exact
mechanism and every hand-fix.

In short: touching `reference.json` (new Pokémon, new forms/costumes, data
corrections) needs no manual version bump. Touching the *shape or meaning*
of a personal table (including a column's on-disk type) needs a
`CURRENT_PERSONAL_SCHEMA_VERSION` bump plus editing
`src/db/schema/personal.ts` and running `npm run db:generate`.

## Suggested schema (starting point, not a mandate)

This is a reasoned proposal reflecting how the game's mechanics actually
work, not a fixed spec. If you (Claude Code) notice something that would be
better modeled differently — a missing edge case, a normalization that
doesn't hold, a game mechanic this gets wrong — propose the change and ask
rather than silently deviating or silently complying. I'd rather be asked
than have you guess.

```text
REFERENCE (replaceable wholesale on every update, keyed by permanent slug)

species
  slug PK, dex_number, name, family_slug,
  gen, rarity (standard | legendary | mythical | ultra_beast),
  region_slug FK -> regions,
  has_male bool, has_female bool,   -- both false = genderless/unknown (e.g. Ditto)
  can_mega_evolve bool,             -- mega is species-wide, never form-specific
  can_gigantamax bool

regions
  slug PK, name

types
  slug PK, name

backgrounds
  slug PK, name

form                     -- one row per catchable form/costume/gigantamax,
                          -- SPLIT BY GENDER: every species with has_male
                          -- and/or has_female true gets separate form rows
                          -- per gender per form/costume
  slug PK, species_slug FK,
  form_name, costume_name (nullable),
  gender (male | female | unknown),
  evolves bool,           -- varies per form (costumes often can't evolve;
                           -- this is separate from mega, which doesn't vary)
  shiny_available bool,
  shadow_available bool,
  dynamax_available bool,
  regional_exclusive bool,
  image_ref TEXT

form_types                -- many-to-many (dual typing)
  form_slug FK, type_slug FK

mega_variant               -- one row per (species, X/Y/Primal) that's real
  slug PK, species_slug FK, variant (X | Y | Primal | null)


PERSONAL (never touched by reference updates)

schema_version
  version INTEGER         -- structural schema version (currently 10;
                           -- see CURRENT_PERSONAL_SCHEMA_VERSION in
                           -- src/db/schema.ts, which is the real source of
                           -- truth -- this comment is a pointer, not a
                           -- second copy to keep in sync by hand)

profile
  id TEXT PK,              -- UUIDv4, generated at profile creation
  username TEXT,
  friend_code TEXT (nullable),
  is_current bool,          -- invariant: exactly one profile row is true
                             -- at any time; this is how "the active
                             -- profile" is tracked, not an app_settings key
                             -- (that would be circular -- looking up a
                             -- setting requires already knowing which
                             -- profile's settings to read)
  created_at INTEGER (epoch ms)

app_settings                -- now per-profile, not global (Sub-project 7a)
  profile_id FK -> profile, key TEXT, value TEXT,   -- PK (profile_id, key)
  -- key-value store for app-wide settings and sync states, scoped per
  -- profile (theme, grid badge picks, indicator selection, etc.)

app_meta                    -- NEW: global, NOT profile-scoped
  key TEXT PK, value TEXT
  -- holds values that are genuinely device-wide rather than per-profile,
  -- e.g. reference_data_version (see src/db/reference-sync.ts) -- this
  -- can no longer live in app_settings now that table's profile_id column
  -- is NOT NULL with a REFERENCES profile(id) FK

species_personal
  species_slug FK, profile_id FK -> profile,        -- PK (profile_id, species_slug)
  registered, xxl, xxs, purified              -- bool

form_personal
  form_slug FK, profile_id FK -> profile,           -- PK (profile_id, form_slug)

  caught bool,
  shiny bool,
  floor bool,                    -- lowest possible IV for a NORMAL catch
  four_star bool,
  shundo bool,                   -- independently stored shiny+hundo

  lucky bool,
  lucky_shiny bool,
  lucky_floor bool,               -- lowest possible for lucky (12/12/12)
  lucky_four_star bool,
  lucky_shundo bool,

  shadow bool,
  shadow_shiny bool,
  shadow_floor bool,              -- lowest possible for shadow
  shadow_four_star bool,
  shadow_shundo bool,

  dynamax bool,
  dynamax_floor bool,
  dynamax_shiny bool,
  dynamax_four_star bool,
  dynamax_shundo bool,

  lucky_dynamax bool,
  lucky_dynamax_floor bool,
  lucky_dynamax_shiny bool,
  lucky_dynamax_four_star bool,
  lucky_dynamax_shundo bool,

  best_shiny TEXT,               -- freeform user-entered value, e.g. "98%".
  best_non_shiny TEXT,           -- NOT derived from the booleans above
  best_lucky TEXT

form_background_personal      -- junction: which backgrounds you own on which forms
  form_slug FK, profile_id FK -> profile,
  achievement_field TEXT,      -- e.g. 'caught', 'lucky', 'shadow_shundo', etc.
  background_slug FK,
  PK (profile_id, form_slug, achievement_field, background_slug)

mega_personal
  mega_variant_slug FK, profile_id FK -> profile,   -- PK (profile_id, mega_variant_slug)
  evolved bool, shiny_evolved bool

personal_data_quarantine      -- stores personal rows that sync finds orphaned
  id PK AUTOINCREMENT,
  source_table TEXT,
  slug TEXT,
  payload_json TEXT,
  quarantined_at TEXT
```

## Reference data ingestion

- **Asset bundling**: The reference data (`reference.json`) is packaged directly within the application binary.
- **Null safety**: Ingestion scripts and tables are tolerant of missing optional fields, allowing incremental completion.
- **Sync mechanism**: Upon startup, if the bundled content hash doesn't match `reference_data_version`, reference tables are reloaded inside a transaction.
- **Gaps visualization**: An in-app "coverage report" allows tracking missing fields, driving the CSV corrections loop.

For details on running the ingestion scripts, the required sequence, and known pitfalls, see the canonical [docs/ingestion-runbook.md](docs/ingestion-runbook.md).

## Future direction (deferred, not yet built)

These are decisions that have already been made — reasoned through and
deliberately deferred, not open questions. They live here because this is
the database design documentation; refer to [features.md](features.md)
for the active specs and the future roadmap trackers.

### Build-time SQLite generation

The CSV→`reference.json` ingestion pipeline described above already exists
and runs at *authoring* time (`npm run ingest:build`). A further step —
pre-baking an actual on-device SQLite file at *app build* time, instead of
the app performing ~8,100 sequential inserts on first boot/reference-data
update — is a separate, deferred optimization.
`@tauri-apps/plugin-sql` has no equivalent to `@capacitor-community/sqlite`'s
former `executeSet`/`importFromJson`/`copyFromAssets` bulk-import helpers —
any pre-baked-database approach here would need to go through `plugin-fs` to
stage a file and `plugin-sql`'s regular `execute` for statements, which is a
different shape than what this section originally proposed. `scripts/build-dummy-db.ts` already proves the
prepared-statement bulk-insert pattern works in this codebase; it's just not
wired into the app's boot path yet. **Deferred**, pending real-device timing
data — see [features.md](features.md#planned-deferred-features) for the bulk edit pagination and optimization details.

### Personal/reference database file split

Today's design — one SQLite database, two logical table groups, joined by
permanent slug foreign keys — is what makes reference-table replacement safe
without touching personal data (see "Storage" above). A further step —
splitting personal and reference data into two *physical* database files
instead of one — was considered and **deliberately deferred to V2**, bundled
with the identity/slug rework below. Splitting the files would remove
cross-file FK coupling as a *concern* entirely (a personal row in one file
can't be foreign-keyed to a reference row in another the way SQLite enforces
it today), but that benefit is clearest once identity isn't a slug-derived
string — hence bundling the two. See [features.md](features.md#planned-deferred-features) for the
future roadmap.

### Identity/slug rework

Slugs today are pure display-derived text (`slugify(name/form/costume/gender)`
in `scripts/ingest/slug.ts`) — there's no PokeAPI numeric ID or other stable
identifier persisted anywhere. That's a real fragility (a display-name typo
fix becomes a slug change, which is exactly what the slug-rename registry in
`src/db/slug-renames.ts` exists to patch over) but fixing it is bigger than a
single-version pass, so it's **deferred to V2**. The insight worth preserving:
identity should likely be unified with the image-pipeline's numeric IDs (see
[features.md#4-sprite-asset-pipeline](features.md#4-sprite-asset-pipeline)) — Niantic's own game-master
form/costume ID enum — rather than solving slug-stability and image-matching
as two separate problems. See [features.md](features.md#planned-deferred-features) for the future roadmap.
